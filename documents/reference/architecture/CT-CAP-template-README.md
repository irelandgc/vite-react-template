# CRR criteria as computable rules — CT Chest, Abdomen and Pelvis (Adult) template

Working proof that the national criteria can be published as a versioned, testable rules bundle that the Criteria Viewer, the Triage Advisor and structured referral forms all consume, with the LLM confined to extraction. CT CAP Adult was chosen because it is the exam with the most compound logic on a single page (pp.10–11 of the April 2026 criteria) and because the earlier Gemini sample started there.

Status: **engineering-complete, not clinically reviewed.** Every rule is annotated with the verbatim source wording so review is a side-by-side check. Six points of ambiguity in the published wording are listed below and need a clinical decision before this is used for anything.

## What is in the package

| Path | What it is | Who consumes it |
|---|---|---|
| `cql/CRR_CTCAP_Population.cql` | The retrieval path (dormant). Derives answers from coded patient-record data: lab flags and values from `Observation.interpretation`, persistence on repeat testing from two abnormal results ≥ 21 days apart, weight-loss % and period from recorded weights, prior CT CAP / US within window from `DiagnosticReport`. Emits answers marked `retrieved` with source references. Codes are placeholders pending NZHTS validation. | Pipeline stage 4, when a retrieval tier is enabled |
| `tooling/populate.mjs` | Stages 4 and 5: runs the population library and merges its answers into the note-derived QuestionnaireResponse (retrieved › documented › inferred), recording discrepancies. | Triage Advisor pipeline |
| `cql/CRR_CTChestAbdomenPelvis_Adult.cql` | The rules. One named `define` per criterion, sub-criterion and redirect; every clinical define carries a `SOURCE:` comment quoting the PDF. Two parameters: `Documentation Standard` (strict / inferred, BRD TA-010) and `P2 Structure Reading` (review Q1). | Triage Advisor engine; structured-form evaluation |
| `fhir/Questionnaire-CRR-CT-CAP-Adult.json` | The indicator catalogue: 30 atomic clinical indicators (plus 6 optional lab values) with stable `linkId`s. This is the single input contract. 19 items carry an SDC `initialExpression` naming the population-library define that can fill them from the record; the rest are clinical judgements and never are. | LLM extraction output; referral form fields; Criteria Viewer tick-list |
| `fhir/PlanDefinition-CRR-CT-CAP-Adult.json` | The published structure and wording: timeframe rows, indication groups, compound composition (`selectionBehavior` all / one-or-more / any), badges (MANDATORY, LAB VALUE REQUIRED, GATEWAY), guidance text, sources. Each action's `condition` names a CQL define. | Criteria Viewer rendering; Admin tool editing surface |
| `fhir/regions.json` | Regional delivery configuration: region codes and the HealthPathways domain for each instance (placeholders). Region is chosen at render time by URL parameter (CV-021) and never reaches the rules. | Criteria Viewer / renderer |
| `fhir/RegionalOverlay-*.json` | Regional overlay: a PlanDefinition derived from the national one that adds "how and where" text and links against national action ids. Structurally cannot carry conditions, inputs or a library; the build rejects one that does. The Te Waipounamu file is illustrative placeholder content. | Criteria Viewer / renderer; regional CRR hubs |
| `elm/*.json` | Compiled ELM (what the engine actually loads at runtime). Regenerated by `npm run build`. | Runtime |
| `extraction/extraction-contract.md` | What the LLM must produce and the rules it must obey (evidence status + verbatim quote per answer; omit rather than guess). | Triage Advisor prompt / validation gate |
| `tests/scenarios.mjs` | 20 scenarios (22 runs). S01–S14 are note-only; S15–S20 supply a patient record and exercise the retrieval path: repeat confirmation computed from two results 28 days apart, repeat *not* confirmed at 10 days, the fabrication case resolved from recorded weights, a prior CT found in the record the note omitted, and a note-vs-record discrepancy. | Regression suite; seed for the clinician-set benchmark |
| `tests/results.md` | Full advisory output per scenario, generated. | Clinical review |
| `tooling/` | `npm run build` (CQL → ELM), `npm test` (scenarios), `npm run check` (cross-artefact consistency). Pure Node.js. | Developers / CI |

## Run it

```
cd tooling
npm install
npm run build     # CQL -> ELM, both libraries
npm test          # 22/22 scenario runs
npm run check     # PlanDefinition <-> Library <-> Questionnaire <-> scenarios consistency
```

Requires Node 22. No Java.

## The architecture this demonstrates

```
 free-text note ──► LLM extraction ──► QR (documented / inferred) ─┐
 structured form ────────────────────► QR (documented) ────────────┼─► merge ─► CQL engine ─► Advisory
 Criteria Viewer ticks ──────────────► QR (documented) ────────────┤              ▲
 patient record (dormant) ─► population library ─► QR (retrieved) ─┘              │
                                                                                  │
            published bundle: Library (ELM) + Population Library + PlanDefinition + Questionnaire, versioned
```

The full architecture (information, application, infrastructure) is drawn in the published page *CRR Decision Support Architecture*.

The engine output (`Advisory`) is one object: determination, priority code and timeframe, active redirects, unconfirmed exclusions, missing-information checklist (linkIds), inferred indicators, and a full rule trace. The referrer view and the triager view are two renderings of the same object, not two evaluations.

Three-valued logic is used deliberately: `true` met, `false` not met, `null` cannot be determined. "The note doesn't say" produces a missing-information prompt, never an assumption. See `S03` vs `S04` in the results: identical presentation, labs unknown → *insufficient, please supply labs*; labs documented normal → *criteria not met*.

## Findings from building it

**The translator is now pure JavaScript.** `@cqframework/cql` 5.2.0 on npm is the official HL7 CQF translator (Kotlin multiplatform build) and compiles FHIR-model CQL in Node with no JVM. Execution is `cql-execution` + `cql-exec-fhir`. The Java dependency I flagged as a tooling risk no longer exists. The package is labelled beta and needs `system-modelinfo.xml`, `fhir-modelinfo-4.0.1.xml` and `FHIRHelpers-4.0.1.cql` supplied (in `tooling/`), which are taken from the CQF repository.

**LLM-written CQL will contain silent semantic errors; the tests are not optional.** Two were caught only by the scenario suite: a CQL query returns *distinct* elements by default, so `Count(flags where flag is true)` returned 1 when two labs were abnormal; and `Count` ignores nulls, so the "unknown labs" count was always 0. Both compiled cleanly and would have produced confidently wrong verdicts (S02 refused a valid B2 referral; S03 never asked for the missing labs). This is the same failure class as the fabrication finding, in a different layer. Every exam/site needs its own scenario suite written from the criteria before the CQL is trusted, ideally by someone other than whoever wrote the CQL.

**Compound criteria decompose cleanly once the atomic indicators are named.** The CT CAP P2 row is `A AND (B1 OR B2 OR B3)` where B2 is itself `age/sex AND weight-loss AND (≥2 of 6 labs AND persistent AND unexplained)`. In the PlanDefinition this is `selectionBehavior: all` / `one-or-more` nesting; in CQL it is named defines composed with `and`/`or`. The Criteria Viewer's CV-014 rendering can be generated from the PlanDefinition nesting rather than hand-coded.

**One indicator, two roles.** "Localising features identified" is simultaneously the negated half of criterion A and an alternative-management redirect. Modelling it once (`workup.localisingFeatures`) avoids the contradictory-output failure seen in evaluation (not-funded yet likely-to-proceed): the engine cannot both satisfy A and fail to redirect.

**The retrieval path is designed in and proven, but dormant.** S15–S20 feed FHIR Observations and DiagnosticReports through the population library. Three things worth seeing in the results: "persistent on repeat testing after three weeks" becomes a computed fact (S15 true at 28 days, S17 false at 10 days) rather than something a referrer has to remember to write; the fabrication case disappears when weights are in the record (S18: 7.5 % over 3.9 months, `retrieved`, P2 in strict mode); and even with full retrieval `lab.unexplained` still has to come from the referrer (S15 asks for exactly that and nothing else), which is the right division of labour. Enabling any tier is a governance event: the PTA and IPP 3A analysis must be redone for that read path first, and the placeholder codes must be replaced with NZHTS-validated bindings — the build's terminology step is where that is enforced.

**The fabrication case is now a test, not a hope.** S06 is the "80kg → 74kg" note. The LLM contract requires the computed 7.5% to be labelled `inferred` with the quote. In strict mode the engine returns *insufficient information* and lists `weightloss.percent`, `weightloss.periodMonths` under `inferredExcludedByStrictStandard`; in inferred mode it returns P2. Which mode is right is a clinical governance decision (TA-010) that can now be made with the behaviour visible.

## Regional delivery, page references and sources

Three distinct things, kept apart on purpose:

- **Evidence sources** (the Source column in the PDF) are national, fixed, and sit in `PlanDefinition.relatedArtifact` as citations. The Canterbury and Cwm Taf HealthPathways entries there are evidence the authors cited, not the local pathway a referrer should open.
- **Page references** sit on every action that carries logic: a `documentation` entry naming page and row, a page-anchored link into the published PDF (host placeholder), and a `source-page` extension so the Viewer can render "see p.11" without parsing labels. The build fails if a logic-carrying action lacks one.
- **Regional content** is an overlay. The national bundle stores the HealthPathways *page ID* once (the seven instances share page IDs; only the domain differs, per CV-012); `regions.json` maps region to domain; a regional overlay PlanDefinition adds delivery notes and links against national action ids. The consistency check enforces that an overlay names a configured region, derives from the national PlanDefinition, targets only existing national actions, and carries no logic. That makes "regions can't change the criteria" a build property, not a policy.

If a region ever needs genuinely different *criteria* rather than different delivery, the architecture can hold a separate versioned bundle with the region in its use-context, but that breaks national consistency and should stay locked unless governance opens it deliberately.

## Clinical review questions (decide before use)

| # | Where | Question | Reading encoded |
|---|---|---|---|
| Q1 | P2 bullet structure | B3 (specialist/PCRL/radiologist advice) is printed as a sub-bullet under criterion A's "AND". Is it really conditional on the full work-up (A AND (B1 OR B2 OR B3)), or does specialist advice stand alone ((A AND (B1 OR B2)) OR B3)? | Literal by default; parameter `P2 Structure Reading = 'alternative'` switches. Scenario S09 shows the difference. |
| Q2 | Weight loss "over 3–6 months" | Is loss over a shorter period (e.g. 5% in 6 weeks) excluded? Over a longer one (8 months)? | Period must be 3–6 months inclusive. |
| Q3 | "documented weight loss" | Does "documented" require recorded weights, or is patient report acceptable? | Recorded weights required (`weightloss.measured`). |
| Q4 | "Male over 50 / female over 60" etc. | Is age 50 included? | Strictly greater than (50 excluded). S13 tests the boundary. |
| Q5 | Precedence | Not-funded → redirect → paediatric → criteria. Should a redirect (e.g. recent CT) outrank not-funded, or vice versa? | Not-funded first. |
| Q6 | Abnormal labs | "raised CRP, low haemoglobin …" are lab-flag judgements. Should the tool take the lab's abnormal flag, a national threshold, or the referrer's statement? Values are captured but not used. | Referrer/lab flag as boolean. |

Also to confirm: yellow-flag symptoms are captured but do not affect eligibility (the criteria say "+/-"); unknown exclusions do not block a P2 determination but are surfaced to the triager (S14).

## What this does not yet do

- Terminology binding. No SNOMED/LOINC codes are asserted on the Questionnaire items — better absent than wrong. Binding to NZHTS reference sets is a follow-up and slots into `Questionnaire.item.code`.
- Runtime packaging. The engine runs in Node; it has not been exercised inside a Cloudflare Worker. `cql-execution` is plain JS and should run there, but that needs a test.
- The evidence extension has no StructureDefinition yet; the URL is a placeholder under `crr.health.nz`.
- Only one exam/site. The value of the approach is that the next one reuses the plumbing (the first 120 lines of the CQL, the whole population library pattern) and only the SOURCE-annotated defines change.
- Retrieval is proven against synthetic FHIR resources, not a real PMS or national API. Tier 2 (form prefill) needs a per-platform mapping to linkIds; Tier 3 needs an actual FHIR source and its consent model.
