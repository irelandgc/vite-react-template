CRR Decision Support Architecture

Target architecture for the criteria tools: the national criteria published as a versioned, testable rules bundle; the LLM confined to extraction; deterministic evaluation; and a retrieval path to referrer systems designed in from the start, dormant until enabled.

Three levels, each one picture. Solid elements are in scope for the next build. Dashed violet elements are built into the design now but not switched on initially. The amber boundary marks where the privacy and residency analysis changes.

Level 1

Information architecture

What the data is, who owns it, and how each thing derives from or conforms to another. The rules bundle is the only thing that persists; everything in the middle column exists for the duration of one assessment.

Ownership

The bundle is owned by the same clinical process that owns the published criteria. A change to a criterion is a versioned change to the bundle, reviewed as a diff, with the scenario tests re-run. The prompt is an engineering component, not clinical content.

Evidence, not verdicts

Every answer says how it was established. Strict mode accepts only documented and retrieved; inferred values are listed for confirmation rather than silently used. This is the structural fix for the fabrication finding.

Codes are metadata

Terminology bindings sit on Questionnaire items, not in the rules. Adding a code changes nothing in the logic; it enables coded input to be mapped onto a linkId when the retrieval path is switched on.

Level 2

Application architecture

The components and the order a referral moves through them. The Triage Advisor is a pipeline of small, separately testable stages; the publishing service is what makes the bundle trustworthy before the runtime ever loads it.

Why a pipeline

Each stage has one input and one output and can be tested alone. The validation gate is what makes the extraction contract enforceable; the merge stage is where the three input paths become one, so the engine has a single code path whatever the source.

Retrieval tiers

Tier 1 is BRD TA-005 and works now. Tier 2 uses the prefill that HealthLink, ERMS and BPAC forms already do from the PMS, mapped once per platform onto linkIds. Tier 3 is a FHIR fetch from the PMS or a national platform driven by the Library's own data requirements.

What the LLM cannot do

Reach the rules engine, assign a priority, assert a value without a quote, or see an unredacted note. Its whole surface is stage 2, which is also the only stage that changes when the model changes.

Level 3

Infrastructure

Where things run and where the boundaries are. Two are fixed by policy: the LLM endpoint must be under Health NZ control (the NAIAEAG test), and no patient data is stored by the tools. The application hosting platform is a decision still to be made; the diagram shows the current prototype and the target side by side.

Decisions this level is waiting on

Application hosting platform under HNZ control (the prototype's Cloudflare control plane is offshore). LLM provider under the HNZ Azure tenancy. Retention period for audit records. Whether the triager view requires HNZ identity.

What does not change with the retrieval tiers

The hosting, the registry, the pipeline, the LLM boundary. Enabling Tier 2 or 3 adds a read path from a system of record into the population service, and requires the PTA and IPP 3A analysis to be re-done for that path first.

Prototype-to-target

The rules engine, bundle format and tests are already platform-neutral Node.js. Moving from Workers to an HNZ platform is a hosting change, not a rewrite; the same ELM bundle runs unchanged.

Open questions carried on all three levels
Q1–Q6
Clinical readings of the CT CAP wording, listed in the template README; decided by a Community Radiology Lead before the bundle is used.
Hosting
Which HNZ-controlled platform hosts the API and engine; drives the residency answer for the application tier as well as the LLM tier.
Retrieval consent
Under what consent and access rules the tool may read a patient's record on the referrer's behalf; different for form prefill (already happening) versus a direct FHIR read.
Terminology
NZHTS binding of the indicator catalogue; who owns the CRR-specific codes for indicators that are assertions rather than clinical findings.
Admin tool
Developer-mediated change path with diff review versus a structured editor; BRD AD-002 needs revising either way.
