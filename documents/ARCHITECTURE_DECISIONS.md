# CRR Tool Suite — Architecture Decisions Register (ARCH-MIG-01)

**Purpose:** the durable record of design decisions made during the rules-bundle migration, so they do not live only in chat history, PR descriptions or one session's notes. Companion to `SECURITY_DECISIONS.md` (SD/SR) and `instructions/arch-mig-known-issues.md` (KI).

**How to use this file:**
- Append-only. Supersede, don't rewrite (`Superseded by AD-xx`).
- `AD-xx` = a design decision. Status is one of **Accepted** (in force), **Proposed** (recommended, awaiting the named decider), **Pending clinical ruling** (engineering has encoded one reading; the clinical review pack carries the question).
- A decision that changes bundle content, engine behaviour or what a referrer sees names the slice that implements it and the check that enforces it.
- Both Gary and Claude Code add entries whenever a design call is made. CLAUDE.md points here.

| **AD-01** | 2026-09-05 | **Bundles are keyed by PDF section; published exam/site IDs map onto them.** The source document has 38 exam/site sections; the published exam/site list has 53 entries because the two adult limb X-ray sections and the paediatric limb sections are split by joint (shoulder, humerus, elbow, forearm, wrist/hand; pelvis/hip, femur, knee, tibia/fibula, ankle/foot) with identical criteria. | **AD-02** | 2026-09-05 | **Bundle versions are semantic and tied to logic.** Major = the library's ELM hash changed (any logic change). Minor = metadata, provenance, vocabulary version, overlays, test results, state — ELM hash unchanged. Patch = corrections to non-clinical text. Re-provenancing an approved-draft bundle to the released PDF is a minor bump. A published version is immutable; a re-publish is always a new version. The bundle version is publish history and is **independent of `PlanDefinition.version`**, which is the FHIR artefact's own version and tracks template iterations; `publish` takes `--version`, and the first publish of a site is 1.0.0. `publish` refuses a major bump when the ELM hash is unchanged from the previous version, and refuses a non-major bump when it has changed. | Reviewers and the Admin Tool must be able to read "did the rules change?" from the version alone. S2's first CT CAP publish as v2.0.0 with unchanged logic showed the rule needs enforcing, not just stating. | `publish` version guard; `check --bundle` compares ELM hash across adjacent versions. | **Accepted**. CT CAP's first publish corrected on PR #3 (v2.0.0 inherited from `PlanDefinition.version`; republished at the first-publish version with the same logic hash). |
| **AD-03** | 2026-09-05 | **National red-flag precedence contract.** `CRR_RedFlags.cql` is evaluated first for every assessment. `ACUTE_ASSESSMENT_REQUIRED` stops the pipeline: no exam library runs, no priority is produced, the Advisory carries the fired flags and their published wording. Otherwise `ACC_PATHWAY` stops it with the ACC redirect. Otherwise evaluation continues to each selected exam library, which applies its own internal precedence. Red flag outranks ACC when both apply. An exam library never re-evaluates a red flag and never defines an indicator in the `redflag.` or `funding.acc*` space; a site row that repeats a national red flag is transcribed at the site as a `documentation` cross-reference, not logic. | BRD TA-011/012/013. | **AD-04** | 2026-09-05 | **Red flags the note never raises are silent.** A red flag is gate-shaped: read through `is true`; null does not fire and does not block. Simple (single-indicator) flags that are null are not reported. Compound flags whose stem is true but whose qualifiers are unanswered are reported as indeterminate with the missing qualifiers listed. Red flags are not exempt from the documentation standard: under `strict`, an inferred answer does not fire the flag. | Reporting ~30 unanswered flags on every referral is noise. | **AD-11** | 2026-09-05 | **Modifier wording is not a condition.** "Especially", "typically", "particularly", "e.g.", "including" introduce examples or emphasis; the wording is preserved in the `SOURCE:` quote and listed in the site's transcription notes, never encoded. Numeric wording is literal; every boundary is a REVIEW question. | KI-05 (RP-000) made general. | Transcription brief template; reviewer confirms the list per site (review pack §7). | **Accepted**; per-site instances pending clinical confirmation. |
| **AD-12** | 2026-09-05 | **A published bundle's KV content is immutable; its `state` is not, and lives in D1, not KV.** The bundle JSON written to `bundle:<examSite>:<version>` freezes at publish time (logic, metadata, everything) and is never rewritten. `state` (`transcribed` → `signed-off` → `published`) legitimately changes afterwards with no logic change, so it is tracked in the `bundles` D1 row and overlaid onto `GET /api/bundle/:examSite/:version`'s response rather than baked into the frozen KV blob. A bundle's own embedded `state` field should be read as "state at the moment this version was first written to KV", not as current truth. | Found in slice 2 while testing the full lifecycle live: publishing at `transcribed`, then transitioning to `signed-off` then `published` via the state route, left `GET /api/bundle/.../latest` reporting the stale `transcribed` value baked into the KV blob at publish time — a real bug caught by exercising the transition end-to-end, not by inspection. | `GET /api/bundle/:examSite/:version` queries `bundles.state` for the resolved `(examSite, version)` and overlays it over the KV-sourced object before returning. | **Accepted**. |
