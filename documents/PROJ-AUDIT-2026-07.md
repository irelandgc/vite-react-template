## 5.2 Disagreements

These are the highest-value findings — intent, code, and live state each tell a different story.

1. **"ct_other is missing" vs "ct_other is live."** Every design/audit document from May through early July (`DOC-AUDIT-2026-06.md`, `ta-src-phase0-findings.md`, `claude-code-data-load-instructions.md`, `prompt-v3-phase0-audit.md`) treats `ct_other` as a known gap — a site the system can't see. It has, in fact, been live in the published D1 data since at least the 14 May 2026 publish (confirmed by this session's direct API check). What's actually true is narrower and easy to miss: the *Triage Advisor* genuinely cannot see it (separate `EMBEDDED_MATCH_DATA` blob, confirmed stale), and the *Viewer's offline fallback* can't see it either (separate embedded blob, dated March), but the *Viewer's live, API-fed path* has had it all along. Three code paths, three different truths, and every document conflates them into one.

2. **Prompt promotion history vs. governance record.** The release log's own 24 May entry said v2.2.0 was active and v2.3.0 "not promoted." It was wrong — v2.3.0 has been live since the day it was created, with two known regressions, and nobody recorded when or why the promotion actually happened. `VERIFICATION-2026-06-21.md` surfaced this and left it as an open question for Gary six weeks ago. It is still open. This is a governance record correcting itself after the fact, not before.

3. **Rate limiting "exists" vs. "protects."** SECURITY_DECISIONS.md and this session's code check agree rate limiting exists on the upstream API worker. But the specific vulnerability (SR-02) is that the *new* proxy design would collapse all client IPs into one shared bucket, defeating the very rate limits that already exist. "Rate limiting is implemented" and "this deployment is rate-limited" are different claims, and several documents elide the difference.

4. **PDF Import: three stale documents vs. current code.** `document-audit.md`, `PROJECT-STATUS.md`, and `crr-roadmap.md` all describe PDF Import as present or planned. The code removed it. This is a straightforward doc-lag case, not a real disagreement about direction — but it's exactly the kind of drift that misleads a cold-start session if those three files are read before the code.

5. **The "TA-REG-01 gate" is cited constantly but was never itself built.** Four separate documents (`ta-src-design.md`, `ta-src-phase0-findings.md`, `prompt-v3-phase0-audit.md`, this brief) treat "the TA-REG-01 baseline" as an established checkpoint to gate future work against. No such artefact exists under that name. TA-REG-02 is real, thorough, and routes through the correct API — but it measures a different variable (prompt version × override, not pre/post criteria-source-switch) and was never relabelled or repurposed as the TA-SRC-01 baseline it's implicitly being treated as satisfying.

## 5.5 Honest one-paragraph summary

The project is in reasonably good shape at the data and documentation layer and genuinely stalled at the decision layer. Criteria data is loaded correctly and live (473 items, 53 sites, `ct_other` included — several months of "is it there" documentation anxiety turns out to be resolved, just never confirmed against the live API until today). The three big design efforts in flight — TA-SRC-01 (criteria source switch), CC-DESIGN-01 (compound criteria), TA-PROMPT-01 (prompt v3) — are each architecturally sound and each blocked on a human decision that hasn't been made: an unbuilt TA-REG-01 baseline, an unsigned Phase 1 design, and a TA-SRC-01 cutover respectively. None of them have started implementation. The role-aware-view branch is a similar story at smaller scale: the code works in preview but sits behind two independent gates (clinical validation, security sign-off) that are each real and neither trivial. The top three genuinely blocking items are the CC-DESIGN-01 sign-off (blocking the clinical circulation), the TA-REG-01/baseline gap (blocking TA-SRC-01), and SR-01/SR-02 (blocking the proxy merge) — none of these are engineering work, they're all waiting on a person. The one thing found that was thought broken but isn't: `ct_other` and the rest of the "6 missing sites" have been fine in production since mid-May; the anxiety about them was propagating through documents that never re-checked the live API. The one thing thought resolved but isn't: which system prompt is actually live and why — v2.3.0 has been running with two known regressions since 24 May and nobody has said whether that was a decision or an accident.
